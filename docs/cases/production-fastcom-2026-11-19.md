## 关键判断

- 服务端 `queued=0`、`tx_head=peer_ack`、`async_wait_us≈99.4%`：
  采样时 tbtun server 没有待发数据，它在等 HND0 mihomo-tbt4 的本地连接产出数据；
  不是 RateGroup 在这一刻压着不发。
- HND0 直连同一 fast.com 目标 45.9 Mbit/s，说明 HND0 到 Netflix OCA 的网络不慢。
- 256 条路径的 `path_tx` 都活跃（约 1.0–1.6M cells），不是路径数/加入失败导致。
- 本地 `flow_credit` 很大（`.../39571298:258554216/0`），不是简单的接收窗口卡死。
- 因此优先怀疑：HND0 `mihomo-tbt4` 的规则/出站把 fast.com 绕到了慢代理，
  或 tbtun 在该目标的大突发下流控/ACK 路径异常；需要分开测量。

## 双端升级后的下行定位

双端部署 SHA-256 `f2b63e00a90ba5a1734f015b070b3ad0ec2bce947c17e7b476fbc5e63c7d1f56`，生产保持 256 路 TCP。新一轮 15 秒测量：同一 OCA 目标（`ipv4-c109-tyo001-ix.1.oca.nflxvideo.net`）HND0 直连 83.81 Mbit/s，本机经生产代理 12.77 Mbit/s（收到 23,937,024 B，超时）。同批另两个目标经生产代理 8.08 和 8.41 Mbit/s（均超时）。不要把不同 OCA 目标之间的差异当作改动收益。

- 实际服务端代理配置为 `MATCH,DIRECT`；测速时该进程确实连接到了 OCA 地址，系统把连接经 WARP 发出。HND0 普通 `curl` 对观测到的 OCA 地址也使用这条系统路由。端口 `10809` 属于另一个进程，不能当作服务端生产代理的隔离对照。
- 服务端 tbtun 的本地环回接收队列在传输期间约有 0.96–0.99 MB 可读，不是代理供数不足。服务端编码步 grant 有余，第二遍写闸门没有拒绝；单流 8 MiB 的信用多秒耗尽。增加步窗口不能解除单流信用，信用耗尽本身也不能证明额度设置太小。
- HND0 `ss -tinmH state established '( sport = :39443 )'` 前后对同一组 256 路取增量：总 TCP 发送字节中 19.32% 是重传；256 路都重传，255 路的重传比例超过 10%。首轮 TCP 发送 35–42 Mbit/s 后，稳态确认大致 10–16 Mbit/s，重传约 2–5 Mbit/s。采样期间服务端 `fq` 的 drops 未增加；证据不能定位到具体丢包设备，也不能把全部重传当作首次传输丢失。协议 SRTT 升至约 950 ms；干净协议样本和承载 TCP 仍约为 320 ms，两者测的是不同阶段。

原始采集位于本机 `/tmp/tbt-down.PsKiIn`：`remote-journal.log`、`local-journal.log`、`remote-transport.log`、`remote-carriers.log`。归因以同一传输窗口内的增量为准。

复测每次用新的连接；不把握手失败当作下载样本，也不把新连接与长驻生产隧道直接比较。首轮和第二轮使用不同的 OCA URL，只比较各轮内相同 URL 的两次下载。

上线判据：两端日志在整个测速窗口均为 256 路，同一目标交错执行关闭/开启组节拍，比较完整下载速率、TCP 重传字节和客户端实际交付。在拿到重复、同向的收益前，不改生产速率控制、写闸门、窗口或 `RepairWait`。新启动的测试隧道如果只到 254 或 255 路，不以少路运行替代生产配置；首轮和稳态分别观察，避免把连接预热当成优化收益。

组节拍只在影子服务上测试，没有上线。同一 OCA、同一服务端候选二进制，两端测速期间的周期采样均为 256 路：开节拍 **8.52 Mbit/s**（15 秒收到 15,974,400 B，超时），关节拍 **18.11 Mbit/s**（11.58 秒收齐 25 MiB）。开节拍时 `producefail` 在测速区间内从 4836 增至 15749，关闭时无增量；这计数表示载体开始取帧后未生成帧，不等于会话异常或丢失应用字节。该实现的节拍路径需要先解释空取帧与启动行为，再作下一轮对照；这一对照不说明其他节拍方案无效。生产未修改，实验开关未保留在源码。

下一个能区分原因的测量：在同一 15 秒生产下载窗口，从两端采集承载 TCP 的序号、确认号和 SACK，只留包头。对齐同一路径的首次发送、首次到达和重传：重传前已到达就查乱序或延迟确认；首次未到而重传才到就查实际丢失。若缺段集中在发送突发的同一小段时间，再验证减小批次或让发送更均匀是否有效。不能拿累计重传字节直接推导应提高多少冗余。

已做单端先导测量：HND0 抓包头经 SSH 回传，只保住下载起始 3.5 秒，且没有收到抓包结束时的内核掉包统计。在保留片段中，256 路共观察到 6.29 MB TCP 负载，其中至少 1.05 MB 的序号范围在同一路上原样重复；捕到 68 个报告重复接收的 D-SACK。客户端同一轮 15 秒前后，`rcv_ooopack` 在全部 256 路增加，合计 12,439，`data_segs_in` 增量为 19,861；这不意味着 62.6% 的包丢失，单个前序缺段可使后续多个段乱序。先导测量当时没有本机包头，不能量化首次缺段和重复重传各占多少。此轮应用吞吐 2.32 Mbit/s，不用于候选 A/B：抓包回传和测速重叠，而且包头不完整。

## 双端包头复核

用本机 `enp8s0` 和 HND0 `eth0` 同时观察生产 `39443/tcp`；本机通过授权的 `su` 获取抓包权限，不修改服务或网卡设置。两端分别落盘，下载结束后才传回 HND0 记录。两端抓包均报告内核掉包为 0。跨 NAT 用序号、确认号、载荷长度和 TCP 时间戳配对 58,944 个唯一包头，建立了全部 256 路的端口对应。双端原始记录和分析脚本在 `/tmp/tbt-dual.sw6Eug`。

这轮 fast.com 下载 15.001 秒收到 4,227,072 B（**2.25 Mbit/s**，HTTP 200，未收齐 25 MiB）。在 HND0 观测到同一路、同序号、同长度重复发送的 4,757 个序号范围中：

| 本机看到的发送版本（按 TCP 时间戳） | 序号范围 | 字节 |
|---|---:|---:|
| 看到重传版本，没看到首次观测到的发送版本 | 4,639 | 2,849,487 |
| 看到首次版本和重传版本 | 27 | 36,983 |
| 看到首次版本，没看到重传版本 | 8 | 11,221 |
| 两个版本均未以对应时间戳匹配 | 83 | 50,837 |

首次观测发送到首次重传的中位间隔是 629 ms。在这一轮**可按原长度和序号匹配的重传样本**中，4,639 个范围只看到重传版本，35 个看到首次版本。本机也确实报告了重复接收（78 个下行 D-SACK 包头）。这个比例不是全链路丢包率：样本不含重分段的重传、可能受网卡分段／合并影响，HND0 的发送侧采样也不等于包已到公网。证据支持优先查两个采样点之间的缺段，而不是把重传普遍归因于迟到或 ACK 延迟。首轮 HND0 发送一秒峰值约 29 Mbit/s，后续降至约 3–13 Mbit/s；相关性不足以认定发送突发是原因。

在上述 4,639 个只匹配到重传版本的范围里，4,435 个在重传版本到达前还得到本机发出的 SACK 佐证，覆盖 255 路：累计 ACK 尚未跨过该范围，本机已报告收到更靠后的字节，却没有报告收到该范围。这说明接收端当时确实有缺口，不只是包头匹配漏掉了一版。它仍不能区分首版永久丢失与晚于重传才到达，也不能定位具体丢包设备；接口的累计丢弃数没有与这些序号对应，不能据此归因。

排除下载开始后最初 0.3 秒及结束前最后 1.5 秒的首发，按 HND0 首发时刻分桶，只统计至少 8 路有发送的窗口。10 ms 窗口中，同序号、同长度的范围随后被重传的比例中位数为 20.0%，第 10 至第 90 百分位为 7.0%–34.5%；受影响路径数最多的窗口是 27/105 路。100 ms 窗口对应为 20.1%、15.0%–25.3%，最广为 94/201 路。这是重复发送指标，并非对各路径独立性或具体丢包点的检验。样本显示缺段可同时涉及多路，但不支持把整次慢速简化为一次全路径断流。

把首次发送按 10 ms 的发送体积分组：从不足 20 kB 到至少 100 kB，各组同范围重传率为 18.95%–21.58%，没有随发送量稳定上升。常见 TCP 载荷 256、512、1415、1448 B 同范围重传率分别为 19.15%、19.16%、21.70%、18.72%；255 路至少出现一个重复范围。这一轮不支持把固定限速、减小 TCP 段，或剔除一两条路径当作首选。服务端第二道写门在这次严重低速样本中确有拒绝（下载覆盖的秒级样本增加约 1,500），不能把先前较快样本中“没有拒绝”的结果推广到所有状态。步窗口仍有余量，服务端单流信用多次触顶，随后读入约 1 MiB、再等数秒。

独立复核了上一轮的 19.32%：报告窗口内 HND0 生产 256 路发送 35,864,116 B，其中 6,928,242 B 为重传。当前工作树 `dotnet test Tbt.slnx -c Release --no-restore` 通过 385 项测试。两端仍使用 `f2b63e00…`，各 256 路，路由规则 `8890` 仍经 `enp8s0`。这轮没有上线改动，也没有生产提速结论。

同一新取的 fast.com URL，紧接着做五轮生产下载，每轮上限 15 秒，前后均有 256 条承载 TCP。按出场顺序为 **1.90、0、0、0、1.39 Mbit/s**：两轮 HTTP 200 均未收齐，三轮没有 HTTP 响应且收到 0 B。用原始速率计入全部五轮，按总体标准差除以均值得 **124.9%**，不满足 < 20% 的稳定性要求。原始记录在 `/tmp/tbt-prod-stability.qydq_nja`。本机最近一次生产服务启动时 `ExecStartPre` 退出 0，当前规则和路由正确；留存日志中没有本轮整机重启的验收记录。

## 同一生产监听的新旧会话

在不停止原连接的情况下，新客户端连到同一个 HND0 生产监听 `39443/tcp`。旧客户端的一次旁路启动在握手后立即报告 `paths=0` 并退出。异步会话的首条路径从队列取出到登记存在空窗；让协调器独占寿命判定后，旁路成功建成 256 路。测速交替进行，不同时跑两个下载；每组前后本机共 512 条承载 TCP，新会话周期采样均为 256 路。部分旧会话日志缺秒，因此旧会话的路径数只按前后 socket 核实。

|---|---|---:|
| 长驻生产会话 | 4.16、无 HTTP 响应、2.22 | 0/3 |
| 独立新会话 | 16.72、13.88、9.31 | 1/3 |

这个对照把差异缩到会话及其 TCP 连接，不代表重建后能持续保持高速，也不代表首次发送缺段已消失。原始记录在 `/tmp/tbt-session-ab.0j8022g0`。同期 HND0 旧服务主线程 3.012 秒内用掉 284 个 CPU ticks（100 ticks/s），且一次秒级日志记录了 316,701 次主循环迭代；服务端未读取协调器退出写入的唤醒计数，会让已就绪的描述符持续触发空转。

客户端原始计数也显示了数据面差异：第一轮有效下载前后，长驻会话收到约 8,772 帧，连续解码前沿推进 372 步；新会话约 21,595 帧、推进 1,247 步。采样靠近测速边界但并不重合，且长驻第一轮中间缺约 11 秒统计；只比较计数增量，不用它解释逐秒停顿。该批没有按会话隔离的服务端 TCP 重传计数，不能判定新会话是丢得更少，还是更快越过了缺段。

隔离候选修复了异步退出判定、JOIN 和路径变更唤醒、关闭期间已释放套接字的竞态，以及服务端退出通知未清。没有纳入工作树的 32 KiB 写门、异步写槽数或轮预算变更。关闭周期统计后，本机用真实 TCP 连续四轮建立 256 路、字节一致地传输 1 MiB、正常关闭；最后服务端 1.5 秒内空闲 CPU 增量为 0 ticks。复现命令为 `python3 tests/e2e/test_async_lifecycle.py /path/to/tbtun`：原生产二进制在第一轮未能达到 256 路，修复候选四轮通过。这是生命周期回归证据，不是公网吞吐数据。

## 独立审计与回归补充

从原始包头独立复算出 4,435 个有接收端 SACK 缺口证据的序号范围，涉及 255 路；两批新会话对照的中位数也复算出相同的反转。对公网候选 `c5be2b8aeaa9…` 重新跑四轮本机生命周期试验，每轮都建齐 256 路、收齐 1 MiB 并正常关闭，但 HND0 端角色的进程在每次关闭后保留的 Linux `eventfd` 数为 **6、7、8、9**。旧回归漏查了会话通知描述符。补上断言后，同一候选第二轮因 6 → 7 失败；修复版四轮全通过，描述符数量不再随关闭次数增长。修复先停止协调器，再关闭路径、轮询器和通知通道；仍在收尾的 IO 线程不能再向已关闭的描述符写入，未交付的缓存归还池。全量单测 385/385。本地测试仅在命令行关闭 NuGet 审计绕过 `Microsoft.DotNet.ILCompiler` 10.0.12 的 NU1903 构建阻断，未改仓库策略；未据此发布生产二进制。

第四轮普通 TCP 的旧脚本以打开的 socket 数判定本机就绪，未等全组验证登记回执；HND0 也把任意一个字节算作完成，且接收端超时和关闭可使快照只余部分连接。这些问题意味着无法用旧记录还原交付。新的 `tests/e2e/plain_tcp_control.py` 先等每路登记和启动回执，每路用 SHA-256 确认收到的分片，采完发送端连接计数才释放接收端，最后比对整文件哈希。本机回环已验证 256 路同时配对、两端同为 26,214,407 字节且与原文件哈希相同。运行时两端各用同一份随机 16 字节令牌文件；发送端执行 `send <监听 IPv4> <端口> --peer <接收端公网 IPv4> --token-file <令牌文件> --file <目标文件>`，本机执行 `receive <发送端 IPv4> <端口> --token-file <令牌文件>`。只有两端字节数、全文件哈希和 256 路前后快照均一致，才作完整普通 TCP 对照；本机回环数字不代表公网速率。

新工具的第一次公网尝试，同一 `23.246.46.155` 目标 HND0 直连 **104.98 Mbit/s**，生产前后测分别 **1.82、4.46 Mbit/s**（各 15 秒超时，四次连接数快照均为 256）。普通 TCP 在 30 秒登记期限内只收到 **254/256** 路登记回执，没有启动文件发送；这不是下行测得 0 Mbit/s，而是没有吞吐样本。原始记录在 `/tmp/tbt-control-audit.24cF7s`；临时监听已清理，两端生产继续运行。

从已有生产包头按本机时钟重新统计：下载第 2 秒（起点偏移 1 秒）本机观察到 **3.13 MB** 承载 TCP 载荷，所有路径的累计 ACK 合计只推进 **1.72 MB**，223 路至少报告一次靠后的 SACK 块。下一秒载荷为 **1.66 MB**，累计 ACK 反而推进 **2.34 MB**。前者包含重复载荷，后者可在缺段补齐时一次跨过此前已到达的字节；这两个计数反映 TCP 按序进度，不等于应用交付字节。它们支持下行确有跨多路的按序推进停顿，但不能把所有应用层停顿归因于承载 TCP，也不能定位造成缺段的设备。

### 同一时窗的三段推进

用 `/tmp/tbt-dual.sw6Eug/client.headers` 和本机生产服务日志（`journalctl -u tbtun-hnd0 -o short-unix`）对齐同一轮下载。以下边界取本机日志时戳，不按整数秒分桶；累计 ACK 取每路在两个边界及之前最后一次发出的值，再按 TCP 32 位序号相减。只纳入两个边界都有采样的路径。解码进度用 `rx_ack`（之前的步全部解完），不用 `rx_base`（最旧保留步）。本地交付用同一流代的 `RxDelivered - Reserve.Count`；它统计交给本地 socket 的字节，不表示 curl 已经读完。

| 下载起点后的区间（秒） | TCP 累计 ACK 增量（字节） | TCP 路径数 | 收到的协议帧 | 解码前沿推进（步） | 本地交付（字节） |
|---|---:|---:|---:|---:|---:|
| 0.938–1.937 | 1,254,378 | 194 | 1,170 | 3 | 36,500 |
| 1.937–2.937 | 2,369,108 | 255 | 1,661 | 14 | 275,504 |
| 3.937–4.937 | 1,102,149 | 256 | 785 | 5 | 96,944 |
| 3.937–6.938 | 2,655,914 | 256 | 1,900 | 35 | 735,712 |
| 10.938–13.938 | 1,399,969 | 256 | 1,011 | 55 | 1,164,656 |

3.937–6.938 秒内，HND0 发送偏移与授信上限相等，未从上游读入新数据；但本机仍收到承载字节和协议帧。两段三秒区间内，本机分别发出了 3、5 次 `FLOW_STATE`，`Reserve.Count` 的各采样点为 0。第一个区间显示，即便承载没停，跨路径解码与按流交付仍可能推进缓慢。各列统计口径不同；不能用字节差除以 TCP 字节算「隧道损失」。解码器会把已知的源立即交给流处理，不等全局连续前沿推进；流本身仍必须按偏移交付。因此 `rx_ack` 不等于某条流的交付门槛。采样不能定位挡住该流的是哪个源，也不能排除采样间的短暂本地写阻塞。下一轮可在本机记录流的下一待交付偏移、已解的待交付队列，以及填补缺口的源对应的解码步与槽位。

独立复测当前工作树：全量 386 项单测通过；CLI 的托管版在同一构建产物上连续四轮建齐 256 路、校验 1 MiB 并关闭，服务端 `eventfd` 数量不增长。发送唤醒测试覆盖「线程在空队列时订阅读事件，新帧发布后没有对端输入也要发出」；它不强制旧实现恰好在读 `txTail` 与发布 `txHead` 之间排空待发帧，因此不构成该竞态的确定性复现。修复的顺序可从代码核对：先发布帧，再通知线程；线程先重开通知，再读队列。仍没有该补丁的公网速率样本。同一轮复核的普通 TCP 回环也核实了 256 路均有前后快照、两端各交付 26,214,407 B，且 SHA-256 与原文件相同。

| B1 | 10.60 | 6 | 53 |
| B2 | 5.44 | 8 | 57 |
| B3 | 2.60 | 6 | 51 |

A 三次为 **0.34、0（无 HTTP 响应）、0（无 HTTP 响应）Mbit/s**；B 的总体口径相对标准差为 **53.2%**。181 个填补事件中，161 个（89%）由方程恢复。按测速脚本记录的外层起止时刻，全部已知源中方程恢复占 1,783 / 41,200（4.3%）；以相同起点加 curl 记录的耗时截断，则为 1,778 / 41,154，填补事件仍为 161 / 181。这说明纠删码经常补上真正挡住流的源，不说明 89% 的停顿时间来自修复，也不说明恢复用的是常规校验还是 BOOSTER。DATA 类不能区分首发、TCP 重传或协议重发。若要修改修复策略，需要把缺口暴露、NACK、修复包发出与解码完成按同一步对齐，找出延迟占在哪一段。

### 首次尾部 NACK 的计时缺口

独立可控时钟复现：正常接收一步，随后只收到心跳告知还有一个未到的尾步，之后没有新的 socket 事件。旧事件循环只给已经发出的 NACK 设重复截止；首次 NACK 的 20 ms 截止没有登记，等待计算退回到 1 秒保活。现在从接收端的原有缺口条件导出首次截止，仍保留 20 ms 条件和 10 ms 检查间隔，不引入固定轮询。回归用例验证接收端按 20 ms 醒来，且对端收到 NACK 后确实排了修复。该结果证明一种可能放大尾部停顿的机制，不证明它解释了公网主停顿或带来生产提速。

加入回归后，387 项单测和四轮 256 路 TCP 生命周期均通过。下行单变量对照可以只改本机客户端的首次 NACK 定时，把两个同源客户端接到同一个 HND0 影子监听；服务端按会话分别接纳路径，配置和目标都可保持一致。先确认两组均有 256 路，再对 HND0 直连验证过的同一个 IPv4 目标交错测速。旧 HND0 服务端的首路关闭和未建齐问题仍可能挡住对照；不能把未开始的下载记成速率样本，也不能把现有非隔离诊断样本算作这个修复的结果。生产仍未切换。
