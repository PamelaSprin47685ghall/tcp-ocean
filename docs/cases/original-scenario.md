# 原始场景标定：400 ms RTT，每 5 元组 4 Mbit/s

状态：Group 4 标定完成（18/18 格，结果按格子盖戳）。源码行为未改；本页只诊断、提议，不提交功能修复。
配置：`PROFILE=rtt400`（`tests/e2e/profiles/rtt400.conf`）：单向 200 ms，共享链路 1 Gbit/s，
每个 IPv4 TCP/UDP 5 元组 4 Mbit/s 漏桶（突发 32 kB）。裸 TCP 校准见
`docs/cases/wanem-profile.md`。矩阵：路径 8 / 64 / 256（服务端 `--max-paths` 与请求一致，
`run.sh` 断言协商值 == 请求值）、编码窗口 1024 vs 4096、段丢失 0% / 5% / 30%。

测试侧只加了短轮次旋钮（`PING_COUNT`、`SKIP_REF`、`HANDSHAKE_S`、内核计数转储，以及
`TBTUN_NETNS_LOCK_HELD` 必须对应真正持有的锁 fd）。会话/编码/调度二进制来自 main 上的
Group 2 合并提交；每格 `stamp` 记录当时的 e2e 脚本提交。

## 协议

- 每格单独持有 `/tmp/tbtun-netns.lock`，结束后暂停约 20 s，好让并行的 loss-hiding 工人拿锁。
- `SKIP_IPERF=1 SKIP_REF=1`，`PING_COUNT=50`，`seconds=8`。p99 基于 50 个探测（此时 p99
  实质上是负载内最差的一次）。块传输含 400 ms RTT 的慢启动，略低估稳态天花板。
- `HANDSHAKE_S` 最终为 60 / 240 / 400 s（8 / 64 / 256）。客户端 JOIN 串行，256 路在
  400 ms RTT 下默认 10 s 等不到「session up」。
- 窗口钳位保持默认 600 kB（单条 4 Mbit/s 路径在 400 ms 下的 BDP 是 200 kB）。自变量是
  编码 `--window`。
- 服务端峰值 RSS（`VmHWM`）和 CPU 秒来自 `run.sh` 的 `report`。内核计数在清理命名空间
  前转储。`ss` 的 retrans 在会话关闭之后采，几乎总是 0，以 `nstat` 为准。

## 理想值

rho 仍是 main 上的 0.25。计费 IPv4 TCP 段 1455 B，净载荷 1328 B，每四个源 cell 一个校验：

    eta = 1328/1455/1.25 ≈ 0.7302
    pipe = min(paths × 4, 1000) Mbit    # 256 路：元组上限 1024，链路 1000
    ideal = pipe × eta
    window_cap = window × 16 × 1328 × 8 / 0.4 Mbit
    effective = min(ideal, window_cap)

| paths | pipe (Mbit/s) | ideal (rho 0.25) | 窗口 1024 上限 | 窗口 4096 上限 |
|------:|--------------:|-----------------:|---------------:|---------------:|
| 8 | 32 | 23.4 | 433.6 | 1734.5 |
| 64 | 256 | 186.9 | 433.6 | 1734.5 |
| 256 | 1000 | 730.2 | 433.6 | 1734.5 |

256 路 + 窗口 1024 预期被窗口卡住（约 434 vs 730）；窗口 4096 则不应被窗口限制。
实测最大缺口不在这个上限上。

## 最大缺口与机制

按相对理想值，最大的吞吐缺口是 **64 路及以上的上行**：0% 丢失时只有理想值的 3%（64 路
5.7 / 186.9 Mbit/s），256 路窗口 4096 只有 0.5%（3.4 / 730）。同一格子的下行在 64 路 0%
仍有 64–69%。把窗口从 1024 加到 4096 几乎不改 64 路上行（5.7 vs 5.9）。下面四条分开说。

### 1. 多路上行塌缩（64 路 3%，256 路 0.5%；下行 64 路仍有 64–69%）

证据（64 路、窗口 1024、0% 丢失，`sZ0vCT`，协商 64 路）。`echo.py` 的 8 s 上行实际跑了
61.5 s 才写出 44 MB，平均 5.7 Mbit/s：

- 突发（约 18:26:16–18:26:20）：客户端 `frames_out` 曾到每秒 1.5–2.1 万，`tx_head` 冲到
  约 2400，inflight 约 380–400 步，booster 从 278 跳到 2600+。wanem `drop_loss=0`、
  `drop_limit=0`、`drop_tuple=0`。
- 服务端在同一秒 `frames_in` 也有突发（13615），`recovered` 升到 3513，但 `rx_ack`
  只到 1769：解码/交付跟不上入向突发。
- 随后坍缩：客户端 `frames_out` 掉到每秒 50–150，几乎全是 BOOSTER（计数持续爬到 7000+），
  `tx_head` 从 18:26:44 起冻在 2637，`peer_ack` 用了约 40 s 才爬完。服务端 `rx_ack` 在约
  55 s 里只从 1769 走到 2576（约 14.7 步/s ≈ 2.5 Mbit/s 的交付）。
- 客户端下行方向的 `rx_ack` 整段上行期间钉在 563。
- 同一会话的下行块传输是 8.6 s、128.3 Mbit/s（理想值的 68.6%）。服务端发送有 pacing，
  没有把 64 路一次性灌进对端。
- 窗口 4096 的上行 inflight 中位数只有 172、最大 405，远没用满 4096，不是编码窗卡住。
- 256 路、窗口 1024、0%（`HPHqdE`）：空闲 ping 仍好（p99 411 ms），小检查也过了；一进
  上行块传输，`peer_ack` 钉在 582 超过五分钟，`tx_head` 只从 982 挪到 1074，`echo.py`
  在读 8 字节长度头时超时。服务端 CPU 260 s。窗口 4096 能跑完格子，但上行仍是 3.4
  Mbit/s、下行只有 30.1（从 64 路的 128 再掉一截）。5% 时 256/1024 握手 258 s 后上行
  2.2、下行 0，CPU 553 s。窗口 4096、5%（`BgKoyU`）握手 386.6 s 后也协商到 256 路，
  但数据路径是死的（下行 0，`peer_ack` 停在 0，CPU 517 s）：漫长 JOIN 可以留下「已
  up」却不能交付的会话。

机制：客户端上行在 64 条（及更多）内核 TCP 上没有像服务端那样的速率组 / BBR-lite /
NOTSENT 门控，路径一齐把已封装的步灌进服务端用户态 TUN。服务端解码和用户态收包跟不上
这次突发（对会话来说像丢失，尽管 wanem 没有丢），于是进入 BOOSTER/修补风暴；修补吃掉
仅剩的发送预算，`peer_ack` 爬行，`tx_head` 在 grant 仍领先时停止前进（内层 TCP 的
`send()` 也被堵，8 s 的块传输被拉成 61 s）。256 路上还叠了 CPU 饱和：路径数从 64 加到
256 让下行从 128 降到 30，并不是在逼近 730 Mbit/s 的理想。

不是每路径 600 kB 钳位（单路 BDP 200 kB），也不是 1024 步编码窗（64 路没用满；256 路
窗口 4096 同样只有 3.4 Mbit/s 上行）。

提议（先不改 src）：

- 给客户端上行加上与服务端对称的 pacing（速率组 / BBR-lite / NOTSENT 门），避免 64 路
  同时突发进入服务端 TUN。
- 把 BOOSTER/修补预算从「交付滞后」里拆开，滞后时不要用满线路。
- 查服务端用户态 TCP 与解码器在突发下的丢弃/积压（现有内核 `nstat` 看不到 TUN 内丢包）。
- 256 路要单独看每路径开销和 CPU，加路径并没有把共享 1 Gbit 用满。

### 2. 握手时间按路径数线性变差（8: 6.6 s，64: 52 s，256: 206 s）

证据：0% 丢失、400 ms RTT 下三次握手分别是 6.60 / 51.6 / 206.2–206.3 s。
206 / 255 ≈ 0.81 s/路，约等于两次单向 200 ms（连接 + 报价/加入帧和回复）再加一点开销。
5% 时 256 路窗口 1024 是 257.9 s，窗口 4096 是 386.6 s，多出来的是 RTO 和偶发的
长时间卡住。

机制：`Client.fs` 在第一条路径的 `ClientOffer` 成功之后，用

    for id in 1 .. min pathCount maxPaths - 1 do
        bootstrap server host join.Frame windowClamp

串行 JOIN。`bootstrap` 是同步的 `Connect` + 发送头和帧 + 等到回复。`session up` 只在
整个循环结束后才打日志。所以 256 路必须把 255 次往返做完，测试脚本才会认为会话起来了。

提议：并行 JOIN（例如同时 8 条），保留每条路径独立的 bootstrap；路径 0 成功后先打
`session up` 并开始转发，其余 JOIN 在后台补。这两项都不需要改编码或拥塞控制。

### 3. 30% 丢失时会话起不来（rc=1，握手 14–95 s）

证据：30% 的六格全部失败，现象相同。8 / 64 路卡在当时测试脚本的 `HANDSHAKE_S`
（30.4 / 91.1 s）；256 路在「客户端已退出则立刻结束等待」之后分别是 94.8 s
（`8WtVUK`，至少 path 11、14 打出 `Connection timed out`）和 14.2 s（`aHW4aP`）。
服务端日志（`EHdLKW`、`WP2Hrb`，256 路同样）：路径 0 在约 2 s 内起来，紧接着
`group paths=2`（至少一条 JOIN 成功），然后客户端进程带着未捕获异常退出。
客户端日志只有：

    Unhandled exception. System.Exception: path closed during bootstrap
        Client.bootstrap ... Client.fs:line 31
        Client.run ... Client.fs:line 63   // JOIN 循环内部

`bootstrap` 把 `ReceiveTimeout`/`SendTimeout` 设为 10 s，若 `Receive()` 得不到
`IoResult.Progress` 就 `failwith "path closed during bootstrap"`。JOIN 循环只
`with :? SocketException`，`failwith` 抛的是 `System.Exception`，所以整进程退出，
即使路径 0（以及已加入的路径）已经可用，也永远不会打 `session up`。

30% × 400 ms RTT 下，一条 JOIN 的 SYN/握手段很容易丢。TCP 会重传，但 RTO 链（1 s、
3 s、…）加上 10 s 的 `ReceiveTimeout`，在剩下的几条 JOIN 里几乎必然碰到一次超时。
8 路等 30 s、64 路等 90 s，都是当时测试脚本的上限，不是客户端还在工作。256 路
即便把上限放到 400 s，fail-fast 也会在进程死后立刻停。加长 `HANDSHAKE_S` 解决不了：
客户端已经死了。

提议：JOIN 循环捕获所有异常（或至少 `failwith`），记录后继续或重试该路径，不要杀掉
进程；对超时的 JOIN 做有限次重试；路径 0 起来后就宣告 session up。评估 10 s
`ReceiveTimeout` 在 400 ms RTT + 高丢包下是否过短（让内核 TCP 把 RTO 做完）。

### 4. 8 路、窗口 1024、0% 时客户端 SRTT 1305 ms（排队？）

证据（`AzVfF9`，与 `8sMiKe` 窗口 4096 的形态相同）。空闲 ping p99 是 404 ms，负载下
p99 是 603 ms，`minrtt_ms` 整段都是 400–401。但上行块传输开始后约 4 s：

    19:06:21 srtt=407  infl=189  peer=697  rtt_skipped=276
    19:06:22 srtt=1370 infl=188  peer=835  rtt_skipped=282   # 一秒内跳到 1.37 s
    … srtt 钉在 1369–1371，直到这块传输结束

Karn 在这一秒里只跳过了 6 个样本（276→282），其余确认都进了 SRTT。从 EWMA
`srtt + (sample-srtt)/8` 反推，一次约 8 s 的样本就会把 407 推到约 1358，与 1370 吻合。
之后 `minrtt` 仍是 400，说明同时还有干净的 400 ms 样本，只是最小值跟踪把它们记下了，
SRTT 没有被同样钳住。

机制：`TxHalf.OnPeerAck` 把样本定义为 **封步时刻到对端 custody 确认**
（`now - sealNs[ack-1]`），不是路径上的 RTT。Karn 只丢掉「封步之后开过修补轮」的样本，
挡不住解码滞后、突发后打包确认、或封步后在发送队列里排队。一次很大的 seal-to-custody
样本就会把会话 SRTT 抬到约 1.3 s；修补间隔是 1.05×SRTT，会被一起拉长。这主要出现在
8 路、上行突发且对端还能跟得上的时候。64 路上行已经塌成 5 Mbit/s，忙时 SRTT 中位数
反而是 407。

所以不完全是「路径上的 1.3 s 排队」：探测 RTT 的 p99 只有 603 ms。是会话层把 custody
延迟当成了路径 RTT。

提议：把样本钳在 k×minrtt（例如 3×，约 1.2 s，会明显削掉这次 8 s 样本）；或者给路径
可见 RTT（已有 `minrtt` / 路径 SRTT）单独记账，会话修补计时不要用 seal-to-custody；
对「一跳确认很多步」只采用最近一拍封步的样本，避免旧步的排队被一次算进 SRTT。
