# 调查:5% 丢包下行 bulk 偶发"慢模式"(35 Mbit 而不是 ~133)

状态:进行中(本分支 srtt-fix 只加了观测与守护测试,未改行为)。

## 现象

- `drop_synack=1`、4 路径、5% 丢包、冷启动 bulk down:goodput 35.3 / 84.2 / 51.1 / 29.5 Mbit,正常约 133。
- 慢的时候服务端 `tx_head - peer_ack` 稳定在 ~380–400 步、`queued=0`;各路径 inflight 很小,路径 srtt 偏高。
  正常时约 85–110 步未确认 + ~260 排队,两者之和也是 ~400:这是流信用上限,一直起作用。
  所以吞吐 ≈ 400 步 / (封装→对端确认的时间);慢模式下这个时间约 2 s,正常约 0.1 s。
- 一旦进入就持续到结束;进入点可以在开头(冷启动)或中途(run.sh 热会话第二次 bulk down 也出现过一次:63.9)。

## 排除

| 怀疑 | 对照 | 结论 |
|---|---|---|
| 丢 SYN-ACK | A 不丢 133.2 / B 丢 130.6 | 不是 |
| tcpdump | C 抓包 131.6 | 不是 |
| 死路径降级 | 慢运行 demotions=0 | 不是 |
| 整机卡顿 | 慢运行 clock_jumps=0、日志无空档 | 不是(卡顿另有其事) |
| poll 后端 | 72dfadb 3/4 慢,main(epoll) 1/7 慢 | 只是概率不同,epoll 也有 |
| TCP 层重传慢 | 慢运行里 533 个重传 507 个 <100 ms 到达 | 不是 |

## 当前假设(待证)

TxHalf 的 SRTT 样本 = 封装到对端确认的时间,包含了解码等待/修复等待;同一范围的修复轮次要等 1.05×SRTT。
一次慢(冷启动 JIT、CPU 争用)把 SRTT 拉大 → 第二轮修复等得更久 → 确认更晚 → 样本更大,自我维持。
本分支在统计里加了 `srtt_ms`,用来在慢运行里直接看 SRTT;正常运行 srtt_ms≈100。
候选修复(Karn:修复轮次开始于该步封装之后的样本不计)在 /tmp/dbg/karn-srtt.patch,未提交,因为还没有在测试里复现。

## 带 srtt_ms 的复现尝试(本分支 41f2674,同一构建)

| 组 | 条件 | 结果 |

| S1–S3 | 每次重新 publish,冷启动 20 s | 131.8 / 133.2 / 133.8 |

17 次全部正常,一次都没进慢模式;此前约 5/15 慢(72dfadb、caf52e6、ctrl-wire 各有)。
CPU 尖峰会抬高 SRTT,但不会自我维持,所以"SRTT 反馈环"假设**未被证实**,Karn 补丁不提交。
慢模式的特征是 `queued=0` 且未确认 ~380 步,而 CPU 尖峰只让未确认数短时升高、queued 不归零:
触发不是单纯 CPU。下一步:把 srtt_ms 合入 main,让以后任何一次慢运行都带上这项数据;
慢模式再出现时同时看 srtt_ms、客户端 rx_ack 与服务端 tx_head 的差,以及当时整机内存(balloon 日志)。
