# 案例:重发的 SYN-ACK 不带选项 → 单路径永不 ACK → 共享组停摆

修复:77880c0(保存 SYN-ACK 选项 + 降级死路径)。本文用抓包确认因果链,不是推测。

## 复现

`tests/e2e/wanem.c` 的 `drop_synack=1` 丢掉第一个 SYN-ACK,客户端重发 SYN。
4 路径,5% 丢包,`echo.py bulk down 30`,在 tbe_near 的 tbn 上 tcpdump。

## 旧版本(3d36699)抓包结论(路径 0,端口 36118)

1. 重发的 SYN-ACK 无任何选项(`win 65535, length 0`,无 mss/sackOK/wscale)。
   客户端内核因此:不缩放窗口、不发 SACK、MSS 536。
2. 服务端仍按 wscale 7 解读窗口:`peer_wnd=8388480`(65535<<7),真实窗口只有 65535。
3. 服务端发到相对序号 785084,真实窗口上沿约 171420;83196 个数据段里 82993 个在窗口外,被客户端丢弃。
4. 窗口内一个段(105884:107299)在 wanem 丢失。客户端只能回无 SACK 的重复 ACK,`ack 105885` 从 01:05:18.03 起到抓包结束不变。
5. 窗口内数据(含该洞)只在 17.96–18.02 发过一次,之后**从未重发**:尾部修复只修 "最后一次交付之后发出的段",
   这些全在窗口外(例:seq 683204 被重发 192 次)。没有 SACK,RACK 也看不到这个洞。
6. 该路径 inflight 固定在 625430,计入共享 RateGroup,组进入 drain 后其它 3 条路径也发不出 → 整个会话停摆。
7. (旁支)本次运行服务端在 01:05:25 因 BOOSTER span 崩溃(6e6ce52 已修),之后客户端上行段按 RTO 退避重传到 01:06:10 无人应答,即 "几分钟无 ACK"。
