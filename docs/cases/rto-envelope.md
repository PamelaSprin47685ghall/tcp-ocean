# 客户端丢包隐藏的有界包络

基线：`2bc29689b5fa1a77df57648d7d4d2d10c9c12a99`。本文给出可执行的验收条件，
不声称当前版本已经通过真实内核的零 RTO 验收。协议仍以
[`TBTun-主文档-v2.2.md`](../spec/TBTun-主文档-v2.2.md) 为准。
不改变客户端内核、`rto_min`、默认 `NewRepair=false` 或现有测试断言。

## 1. 分开验收四件事

| 命题 | 需要的证据 | 不能代替它的证据 |
| --- | --- | --- |
| 无客户端内核重传 | 每条载体连接在测量段内 `tcpi_total_retrans` 增量为零，并由客户端出口包轨迹核对旧序号重发 | 没有 RTO；TLP 也可能重发旧序号 |
| 无客户端内核 RTO | 每条载体连接的 RTO 事件增量为零；记录计时器状态和到期时刻 | `TunCounters.Rtos=0`；这个计数属于服务端用户态 TCP |
| 无窗口收缩 | 单独记录客户端 `cwnd`、`ssthresh` 及 TCP 拥塞状态；同时检查服务端通告窗口的右边界不后退 | 没有重传；内核还可能因空闲重启或 ECN 改变 `cwnd` |
| 应用限时恢复 | 从故障解除起，目标前缀逐字节正确，下一次新写入也在预先规定的时间内完成 | TCP ACK 已前进；被吞的源仍可能在等待编码修复 |

“无窗口收缩”若指 `cwnd` 数值从不减少，就必须把目标内核的空闲重启、拥塞算法和
ECN 条件也写进场景。只验证没有丢包导致的降窗时，应把结果写成这个较窄的命题。
接收窗口字段变小不一定是收回承诺；要比较展开后的 `ACK + scaled_window` 右边界。
四项分别给出 `pass`、`fail` 或 `unmeasured`，不得相互推断。

RFC 6298 第 5 节规定了未确认数据的重传计时器及累计确认前进后的处理；
RFC 8985 第 7 节的 TLP 可以重发尾段，且 TLP 失败后仍保留 RTO。
因此，`2 * SRTT` 不是端到端恢复的保证，也不是所有内核的剩余 RTO。
RFC 5681 第 4.1 节说明了空闲后的拥塞窗口调整；RFC 9293 第 3.8.6 节定义了
接收窗口右边界的收缩。参考链接见文末。

## 2. 当前实现先要满足什么

包络针对已完成引导、处于数据阶段、源保留租约有效的客户端载体连接。
HTTP 头、引导帧、第 0 帧、TCP FIN、正在关闭或已失败的路径不在吞洞包络内。
这些字节仍须遵守自己的可靠传输规则。

`TunPath` 的实际顺序是：

1. 本路径收到更高序号的字节，才能观察到其前面的洞。
2. 洞后的累计解码前沿提供充分证据时可以提前吞洞；否则等待固定的 15 ms 宽限。
3. `Service` 到达后执行吞洞，随后 `FlushAck` 才把累计 ACK 写出。
4. 该 ACK 还要走完回程，并由客户端内核处理，才能解除内核的未确认责任。

宽限从洞首次被观察到时计算。后续区间扩展不应重新开始这 15 ms。
本路径的 ACK 不能因为另一条路径已经前进而凭空越过未观察到的尾部。
规范第 6.8.2 节要求 ACK 不超过已观察到的最右字节；`TunPath.leaseValid`、
`addInterval`、`ServiceCore` 和 `FlushAck` 共同执行这一条件。
规范中 15 ms 宽限小于常见最小 RTO 的比较，只涉及这一步的开销；它没有扣除
中断前已经消耗的计时器预算，也没有包含尾洞暴露、回程和调度时间。

**尾洞必须有单独的可见性条件。** 如果最后一个 TCP 段丢失，后面没有同一路的更高
序号字节到达，服务端不知道这段已经发出。仅给出“中断不超过若干毫秒”无法保证零
RTO。当前 `TxHalf.HeartbeatDue` 是会话级条件：空闲且源未获保管确认时，至少间隔
50 ms 才能发 HEARTBEAT；它不是每条路径每 50 ms 必达的承诺。发送窗口已满、队列
忙、路径调度和 HEARTBEAT 本身丢失都可能延迟尾洞暴露。另一条路径收到 HEARTBEAT
能帮助会话发现缺步，但不能单独证明这个 TCP 元组的发送边界。

## 3. 零 RTO 的充分条件

在每个可能阻断累计确认前进的时刻 `t0`，对每条仍有未确认数据的客户端载体路径
`i`，记录或保守界定以下量。所有时间使用同一单调时钟，或带有已知误差的时钟映射。

| 量 | 含义 |
| --- | --- |
| `R_i` | 从 `t0` 起到客户端本次实际 RTO 到期的剩余时间下界 |
| `B_i` | 从 `t0` 起，故障继续阻断所需数据或反馈的最长时间 |
| `E_i` | 故障解除后，到服务端成功收到同一路、更高序号的合法字节的最长时间；包括生成、写门控、发送排队、正向传播和允许的再次丢失 |
| `G_i` | 洞可退休所需的宽限上界；当前普通路径为 15 ms，已证明的快速吞洞可更短 |
| `J_s,i` | 宽限结束后，到 `Service` 和 `FlushAck` 完成并成功提交 ACK 的调度及输出延迟上界 |
| `F_i` | ACK 提交后，至少一份能前进累计确认的 ACK 通过回程的最长时间；包括排队和丢失后的再次反馈 |
| `J_c,i` | ACK 到客户端后，内核处理它的最长延迟 |
| `M_i` | 正的测量、时钟与计时器竞争余量 |

一个保守、可逐项检查的充分条件为：

```text
B_i + E_i + G_i + J_s,i + F_i + J_c,i + M_i < R_i
```

这是严格小于。ACK 与定时器恰好同时发生时，不假定内核先处理 ACK。
若 `E_i` 或 `F_i` 无有限上界，或没有可信的 `R_i` 下界，该路径为 `unmeasured`
或包络外，不能填零凑出通过结论。

相应的中断预算为：

```text
B_max < min_i (R_i - E_i - G_i - J_s,i - F_i - J_c,i - M_i)
```

右侧不为正时，这个初始状态没有可承诺的正中断预算。它不是产品的固定线路参数，
也不是要写进 pacer 的速率常数。上下行的排队、容量和反馈延迟分别测量；不能用
下行估计代替上行证据。受影响路径中最紧的一条决定全组的承诺。

每次累计 ACK 前进后，都必须按实际内核的新定时器状态重新检查。多次中断之间没有
累计 ACK 前进时，不能把每次单独称作“短中断”；它们消耗的是同一份剩余预算。
只收到重复 ACK、SACK 或另一条连接的 ACK，不等于本连接的累计确认已前进。

`TCP_INFO.tcpi_rto` 通常表示当前超时长度，而非此刻还剩多久。验收应观察目标内核
的定时器到期状态，或根据经过验证的计时器重启事件建立剩余时间下界；只有 SRTT、
初始 RTO 或一次 `ss` 快照，不足以补齐这一证据。TLP/RACK 可能重排计时器，须按
实际内核版本解释，不能用 RFC 6298 的简化模型冒充目标内核。
支持 `TCP_INFO.tcpi_total_rto` 的内核可提供每连接累计 RTO 计数；读取前须确认
目标内核的结构长度和字段定义。这个累计计数同样不提供下一次到期的剩余时间。

## 4. 比零 RTO 更强的“内核看不到丢包”

上式只针对 RTO。无客户端内核重传还需要：

- ACK 在本次最早可能重发旧序号的定时事件之前到达；这个界还要考虑 TLP/PTO、
  RACK 和该内核的其他恢复路径。
- 客户端在 ACK 到达前没有收到会触发快速重传或丢失推断的反馈。
- 租约、接收存储、已承诺窗口和源保留责任都有效；成功观察边界的字节不能被内存
  压力拒绝后仍当成已经接收。

这些条件也逐路径检查。没有 TLP 重发不代表没有 TLP 新数据探测；D-SACK 后撤销
降窗也不能把已经发生的重传改记成“零重传”。真收到的重复字节仍按既有 D-SACK
规则处理，不能为了统计好看伪造接收历史。

无 `cwnd` 数值下降还要求测试区间没有独立的空闲重启、ECN 或拥塞算法窗口调整。
不能通过关闭真实事件的统计，或提高 `rto_min`，扩大声称已经验证的包络。

## 5. 包络外仍要保证什么

无限期中断没有有限的恢复时限。包络外的验收从明确的“故障解除且服务恢复条件
成立”时刻开始：至少一条路径持续可用，源和控制状态仍保留，读者能接收，调度有界，
修复和反馈在预先规定的有限次数内成功到达。

在这些条件下分别检查：

1. 已接受的应用字节逐字节一致，无重复、无缺口、无正常 FIN 冒充错误。
2. 保管确认只在责任真正接管后前进；TCP 虚拟 ACK 不能释放源。
3. 修复队列、每轮工作和内存保持各自的既有上界，修复计入节拍。
4. 缺失前缀在预先声明的恢复预算内完成；完成后新的写入也继续前进。

若使用时间公式，须给出最多 `N` 轮可成功修复的假设，再计算检测、每轮等待、发送、
传播、解码和本地交付的总上界。独立随机丢包只能支持带概率的结果；不能由“平均
丢包率 5%”推出每一轮必达的确定性时限。持续不可达超过会话寿命时，正确结果是
明确失败，不能承诺无限保留又承诺有限内存。

## 6. 回归覆盖与真实内核验收

`tests/Tbt.Tests/RtoEnvelopeTests.fs` 补充以下产品行为检查，保留现有 blackout、
no-SACK 和 RepairWait 测试原样：

| 检查 | 证明范围 |
| --- | --- |
| 洞后区间持续增长，在首次发现后 15 ms 仍可吞洞 | 后续到达不续宽限；宽限前不暴露普通洞的 SACK |
| `Service` 与 `FlushAck` 分开迟到 | 15 ms 不是包含事件循环和输出的端到端 ACK 上界 |
| 不可见尾部、另一路独立前进 | 不猜测序号；不能拿其他路径的前进替代本路径证据 |
| 300 / 1300 ms 正向全丢后恢复，两个种子 | 真实会话编码在默认修复策略下保持字节正确、修复结束、新写入继续前进 |

最后一组固定 4 条内存路径、单向 20 ms、每 1 ms 调度一次、恢复后无新增丢包；
恢复限时 2 s 是该测试的断言。这个模型没有客户端内核，不给出零 RTO 或零重传
结论，也不能代替官方 e2e。其余测试固定服务端时间条件，没有验证网络反馈上界。

真实内核矩阵须包括：可见中间洞、整尾丢失、仅回程 ACK 中断、双向全路径中断、
反复短中断但累计 ACK 不前进、ACK 恰好靠近到期边界，以及不对称回程。
每种至少两个有效种子；在边界内外分别取样，事先固定 `M_i` 和应用恢复预算。
真正的内核计数和到期证据缺失时，保留 `unmeasured`，不能据模型测试填 `pass`。

每段保留脚本提交、产品构建提交和二进制 hash、全部生效开关、内核版本、拥塞算法、
SACK/RACK/TLP 与 ECN 状态、协商路径数、种子、各路径身份和测量窗口。载体路径与
本地业务 TCP 分开计数。`run.sh` 末尾的 namespace 总计包含不同阶段的连接，不能
单独证明某条路径在某一段没有 RTO。

对 `host_pause`、stats gap 和 clock jump 仍采用分段有效性规则。产品自己的 CPU/GC
迟到若超出预先声明的 `J_s,i`，这是调度预算未满足，必须报告；不能因为事件循环
空转就从性能比较里删除。服务器的时钟补偿也不能把客户端内核已经走过的 RTO
时间倒回去。
