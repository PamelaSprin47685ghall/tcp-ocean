# 负载下 ping 尾部(p99 100–226 ms)从哪里来

工具:opt-in 跟踪 `TBT_TRACE=<前缀>`(关闭时每个调用点只有一次 bool 判断、不分配),`PING_TRACE`
记录每次 ping 的发送时刻。netns 两端在同一台机器上共用 CLOCK_MONOTONIC,所以跨进程时间可直接相减。
脚本:docs/cases/data/trjoin*.py。事件:交互步封口 / 交给路径 / 客户端收到 / 源已知;
服务端 TunPath 首传段 RTT 样本与在途字节;客户端每次读路径前内核可读字节。

运行(cr 分支 + 跟踪,run.sh 20 ms、200 Mbit、4 路径、10 s,clock_jumps=0):

| 丢包 | 空闲 ping p99 | 负载下 ping p99 |
|---|---|---|
| 5% | 41.7 / 46.3 | 196.5 / 204.6 |
| 0% | 44.3 | 49.1 |

## 分层(5%,200 次 ping,跨进程拼接 200/200)

中位:上行 20.2、服务端回显 0.2、会话发送队列 0.0、**路径 20.3**、解码 0.0、客户端应用 0.2 ms。
最慢 15 次:会话队列 0.0–1.0 ms,解码 0–46 ms,**路径(服务端交给 TunPath → 客户端会话收到)87–221 ms**。
回包的 4 个 Cell 分在 4 条子流上,4 条同时晚到(差 ±5 ms)。

1. 不在会话层:交互队列先于大流量,封口到交给路径 ≈ 0。
2. 不在发送端未发送队列:TunPath 在 CommitFrame 直接写 tun,没有未发送字节。浅队列 Q-1 对下行无对象,
   这也解释了 sq3 A/B 没有改善。
3. 不是客户端读得慢:慢 Cell 等待期间内核可读字节大多只有几十 KB(一次 588 KB 的释放 9 ms 内读完),
   Cell 本身不可读,即停在内核乱序队列里。
4. 与 Cell 同时(±3 ms)发出的段,SACK 的 RTT 为 70–158 ms;Cell 的按序交付比这些段的网络到达
   晚 43–142 ms(中位 74 ms):**TCP 队头阻塞**,等洞前的重传,约 1 个(已被排队拉长的)RTT。
5. 时间上:慢 ping 是连续一段。下载前 ~3 s 内每路在途 ≈ 240 KB、RTT 中位 41 ms,ping 最大 65–96 ms;
   此后每路在途升到 360–730 KB,RTT 中位 60–120 ms,**瓶颈上形成常驻队列**,ping 最大 105–244 ms;
   下载结束即回到 41 ms。0% 丢包时每 Cell 单程 p99 28 ms。

结论:尾部 = 瓶颈常驻队列(组 cwnd = 2 × bw × minRTT,链路接近满载:135 Mbit 有效 + 校验/头/重传)
× 2(排队本身 + 被拉长 RTT 的队头阻塞)。要缩短它,应控制组的在途量/带宽估计(拥塞控制),
而不是会话交互信用或发送端浅队列。

## 跟踪本身的开销

关闭时:每个调用点一次静态字段读取(TraceGate,无类型初始化检查);单元测试证明关闭时 10 000 次 record
分配 0 B。cr 分支上旧写法(模块值)的 A/B 显示服务端 CPU/Gbit +4.6 %(与 CR-2 混在一起,未分开);
新写法的 CPU 将在下一次 A/B 中两臂都含跟踪,单独开销尚未测。
