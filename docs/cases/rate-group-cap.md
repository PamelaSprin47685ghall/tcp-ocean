# 速率组:在途上限 1.25 × BDP,修补计入组节拍(分支 cc)

依据:docs/cases/under-bulk-tail.md(负载下尾部 = 瓶颈常驻队列 + 队头阻塞;组 cwnd = 2 × bw × minRTT)。

改动:
1. 启动后组 cwnd 增益 2.0 → 1.25(启动仍 2.885;已有 1.25/0.75/1×6 增益循环作为周期排空)。
2. 修补副本(HOLE-2,每次 2–4 份)以前只扣路径自己的令牌,组就绪后不受组节拍约束:现在计入组节拍
   (`RateGroup.OnRepair`,`repair_kib` 统计)。被降级的路径不扣组令牌(它已退出组的求和)。
3. 多出的副本也占瓶颈,但不计为已交付,带宽估计因此低于线速 → 节拍螺旋下降(第一次运行下行 −10 %)。
   现在段被确认时,其重复副本字节计入该路径的 Delivered(只算真的送达的)。
4. 组以有效载荷字节计速率样本,节拍却按整包(含 40 B 头)扣:统一为有效载荷字节。

单元测试(TunTests):启动后上限在 [1.25 BDP, 1.25 BDP + 4 帧] 且 < 1.5 BDP;修补耗尽令牌后新帧等待;
一次修补两份副本计入组;重复副本在段被确认后计入 Delivered;一条永不确认的路径被降级后不拖住其他路径。

## 带宽估计被 ACK 突发抬高(068f1f2 的跟踪运行)

第一次下载只有 81.9 Mbit(11.3 s,clock_jumps=0):下载前组估计 336 Mbit(链路 200),启动突发 1.8 MB 在途,
服务端会话 srtt 升到 684–887 ms、未确认步 ≈ 350–380(即之前的"慢模式":修补轮次等 1.05 × SRTT,
SRTT 越大修补越慢)。组的速率样本 = 时间窗内的 Δdelivered;洞被补上后的一次累计 ACK 让样本远超链路
(下载中也见 228/234/375),10 轮最大值滤波把它留住。

修复(BBR send_elapsed 的做法):样本不得超过上一个区间的发送速率(新帧 + 修补副本)。
单元测试:稳态 200 Mbit 时,40 ms ACK 停顿后一次累计 ACK,估计不超过稳态的 1.05 倍。

## 结论(到 feafd2a):不合入,留在 cc 分支

- 常驻队列消失(跟踪:下载全程 RTT 中位 40–41 ms,每路在途 ≈ 225–234 KB;main 为 60–120 ms、360–730 KB)。
- 尾部:cc 两轮 6 次 102.7–127.7 ms,没有 main 的 165.9 / 211.7 这类长尾;但 main 6 次中位 130.8,
  且 main 有的运行不起队列(101–110),所以中位改善不大,远未到 < 80 ms。
- 剩余尾部是队头阻塞:5% 丢包下每条子流几乎总有洞,补洞要约 1 个 RTT(≈ 40 ms),交互 Cell 只有在 4 条子流
  同时被挡时才慢。去掉排队后它就是 41 + ~40 ≈ 80–120 ms 的下限;再降需要交互专用 lane(无大流量挡在前面)
  或更快的洞修复,不是拥塞控制能解决的。
- bulk down 仍低 1.6 %(三次全低):没有队列做缓冲时,按最大值估计的节拍略低于链路。
